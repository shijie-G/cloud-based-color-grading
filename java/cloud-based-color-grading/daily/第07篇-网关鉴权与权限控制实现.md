# 周记第七篇：网关鉴权与权限控制实现

本周主要分析网关鉴权和权限控制模块。系统采用 Gateway 作为统一入口，所有受保护接口都先经过网关再转发到具体服务。JwtAuthenticationFilter 是认证过滤器，主要负责处理 Token 校验。请求进入后，过滤器首先放行 OPTIONS 预检请求和白名单路径，例如 /auth/login、/auth/register、/actuator/** 等；对于其他请求，则从 Authorization 请求头中提取 Bearer Token，调用 JwtTokenProvider 验证签名和有效期，再从 Token 中解析 userId、username 和 roles。

为了防止仅凭伪造 Token 访问系统，网关还会到 Redis 中读取当前用户保存的 Token，并与请求中的 Token 做一致性比较。只有签名有效、未过期且 Redis 中存在相同 Token 的请求才会继续向后传递。Token 剩余有效期小于设定阈值时，网关会自动生成新 Token，更新 Redis，并在响应头中返回新的 Authorization，从而实现自动刷新。认证成功后，网关将用户编号、用户名和角色信息写入请求头，供后续服务使用。

权限控制由 PermissionAuthorizationFilter 完成，该过滤器在认证过滤器之后执行。它从请求头中读取用户编号，然后通过 PermissionClient 调用授权服务，检查用户是否拥有访问当前 path 和 method 的权限。如果授权服务返回 true，则请求继续转发；否则返回 403。授权服务中的 PermissionServiceImpl 会先从 Redis 读取用户权限缓存，如果缓存不存在，则通过 PermissionMapper 从数据库查询用户经由角色获得的权限列表，再写入 Redis。权限匹配时根据 resourcePath 和 HTTP method 判断是否允许访问。本周工作让我理解了认证和授权的区别：认证解决“你是谁”，授权解决“你能访问什么”。
